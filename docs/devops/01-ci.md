# D1 — Continuous integration

**Goal:** nothing reaches `main` unless it is linted, tested, buildable and free of known
critical vulnerabilities — and every commit on `main` produces a ready-to-deploy, verifiable
container image.

## What was added

| File | What it does |
|------|--------------|
| [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) | The pipeline: checks on every pull request, image publishing on `main` |
| [`.github/workflows/codeql.yml`](../../.github/workflows/codeql.yml) | CodeQL static analysis of Python, TypeScript and the workflows themselves |
| [`.github/dependabot.yml`](../../.github/dependabot.yml) | Weekly dependency-update pull requests for pip, npm, base images, Compose images and actions |
| `GET /api/v1/health/live/` | A liveness endpoint, separate from the readiness check at `/api/v1/health/` (needed in D3) |
| Dockerfiles | Production images patch OS packages and drop the build-only tools (pip, npm) |

## The pipeline

```
pull request ──┬── Backend ─────── ruff · ruff format · makemigrations --check · pytest on Postgres 17
               ├── Frontend ────── npm ci · tsc · eslint · vitest · next build
               ├── Secret scan ─── gitleaks over the full git history
               └── Image scan ──── build both production images → Trivy (fails on fixable CRITICAL)

push to main ──── all of the above, then
                  Build  ── 4 parallel jobs: {backend, frontend} × {amd64 on x64 runner, arm64 on ARM runner}
                  Publish ─ stitch each pair into one multi-arch image on ghcr.io,
                            tag sha-<commit> + latest, sign build provenance
```

Images end up at `ghcr.io/adeeshalytics/yathra-backend` and `…/yathra-frontend`.

## Concepts, and why each choice was made

**Service containers.** The backend job starts a real `postgres:17-alpine` next to the runner.
The schema uses Postgres-only features (a btree_gist exclusion constraint stops a bus being
double-booked), so SQLite would hide real failures. Same major version as docker-compose:
"works in CI" should mean "works in production".

**`npm ci`, not `npm install`.** `ci` installs exactly what `package-lock.json` says and fails
if it disagrees with `package.json`. This caught a real bug on day one (below).

**Least-privilege tokens.** The workflow's default `GITHUB_TOKEN` is read-only
(`permissions: contents: read`). Only the jobs that need more ask for it: the image scan may
write to the Security tab, the publish jobs may push packages and sign attestations. A
compromised step in the test job cannot push an image.

**Actions pinned to commit SHAs.** `uses: actions/checkout@3d3c42e…  # v7.0.1`, not `@v7`. A tag
is a movable pointer. On 19 March 2026, attackers with stolen credentials force-pushed 76 of the
77 version tags of `aquasecurity/trivy-action` to credential-stealing malware; for about 12 hours
every workflow that referenced the action by tag ran it
([GHSA-69fq-xp46-6x23](https://github.com/advisories/GHSA-69fq-xp46-6x23)). Workflows pinned to
a commit SHA were unaffected, because a SHA cannot be moved. Dependabot updates the pins (and
the version comments) weekly.

**Three kinds of security scanning.**

| Kind | Tool | Looks at | Finds |
|------|------|----------|-------|
| SCA — software composition analysis | Dependabot, Trivy | Your dependencies | Known CVEs in libraries and OS packages |
| SAST — static application security testing | CodeQL | Your source code | Injection, unsafe redirects, missing escaping, workflow script injection |
| Secret scanning | gitleaks (+ GitHub's own) | Every commit ever made | Keys and passwords committed by accident |

**The vulnerability gate.** Trivy fails the build on a *fixable CRITICAL*. HIGH findings are
printed in the job log and (on `main`) listed in the Security tab, but do not block. A brand-new
HIGH CVE in a base image would otherwise turn every pull request red until the upstream image
is rebuilt — a gate people learn to ignore protects nothing. `ignore-unfixed` hides findings
nobody can act on yet.

**Dependabot cooldown.** New releases wait five days before Dependabot proposes them. Most
malicious package releases are caught and pulled within days; security updates skip the wait.

**Native ARM runners, not emulation.** The Oracle free servers (D2) are ARM. Building arm64 on
an x64 runner means QEMU emulation, which makes the Next.js build several times slower. GitHub
gives public repositories free `ubuntu-24.04-arm` runners, so each architecture builds natively
and in parallel.

**Push by digest, then a manifest list.** Each build job pushes its image *without a tag*,
identified only by its content digest. The publish job creates one *manifest list* that points
at both digests and tags it. `docker pull` then picks the right architecture automatically.

**Immutable tags.** `sha-1a2b3c4` always means the image built from that commit. Deployments
(D3/D4) will reference these, never `latest` — otherwise "what is running?" has no reliable answer
and a rollback is guesswork.

**Build provenance.** Every published image carries a signed statement (SLSA provenance,
signed via Sigstore with the workflow's OIDC identity) of which repository, commit and workflow
produced it. Verify one with:

```bash
gh attestation verify oci://ghcr.io/adeeshalytics/yathra-backend:latest --owner Adeeshalytics
```

**Liveness vs readiness.** `/api/v1/health/` checks the database and cache and returns `503` if
either is down — a *readiness* signal: "don't send me traffic". `/api/v1/health/live/` checks
nothing but the process — a *liveness* signal: "restart me if I stop answering". If liveness also
checked the database, a database blip would make Kubernetes restart every API pod at once,
turning a short outage into a long one.

## What the pipeline found on day one

These were all real, and all fixed in this phase:

1. **The frontend production image did not build.** `package-lock.json` was written by npm 11.6
   on Windows; npm 11.19 on Linux found it missing `@emnapi/*` entries that only Linux installs
   need, and `npm ci` refused. Fixed by regenerating the lockfile with the same npm as the
   image.
2. **A critical remote-code-execution vulnerability in Next.js 16.3.4** (GHSA-vcvr-r3jv-pc5j, in
   `next/og`). Upgraded to 16.3.8.
3. **13 HIGH vulnerabilities in tools the images did not need at runtime** — npm and corepack
   in the Node image, pip (and the urllib3/msgpack copies it vendors) in the Python image — plus
   an unpatched `libpcre2`. The production stages now remove the build tools and apply OS
   security updates. Both images now have zero fixable HIGH or CRITICAL findings.

## One-time GitHub settings (do these in the browser)

The workflow cannot change repository settings; these need you, once.

1. **Protect `main`.** *Settings → Rules → Rulesets → New branch ruleset*: target the default
   branch; enable *Require a pull request before merging*, *Require status checks to pass*, and
   *Block force pushes*. Add these checks (they appear in the picker after the first run):
   `Backend`, `Frontend`, `Secret scan`, `Image scan (backend)`, `Image scan (frontend)`,
   `Analyze (python)`, `Analyze (javascript-typescript)`, `Analyze (actions)`.
   You can let yourself bypass the ruleset as the repository admin, but get used to merging
   through pull requests — it is the habit teams expect.
2. **Security features.** *Settings → Advanced Security*: turn on Dependabot alerts, Dependabot
   security updates, secret scanning and push protection (all free for public repositories).
   Leave CodeQL's *default setup* **off** — this repository uses the workflow instead.
3. **Make the images public** after the first run on `main`: your profile → *Packages* →
   `yathra-backend` → *Package settings* → *Change visibility* → Public. Same for
   `yathra-frontend`. Then the D3 cluster can pull them without credentials.

## Running the same checks locally

```bash
cd backend && ruff check . && ruff format --check . && python manage.py makemigrations --check --dry-run && pytest
```

```bash
cd frontend && npm ci && npm run check && npm run build
```

```bash
docker run --rm -v "$PWD:/repo" ghcr.io/gitleaks/gitleaks:v8.30.1 git /repo
```

```bash
docker build --target production -t yathra-backend:local ./backend
```

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:0.70.0 image --ignore-unfixed --severity HIGH,CRITICAL yathra-backend:local
```

## One image, many environments (solved in D3)

`NEXT_PUBLIC_API_URL` is compiled into the frontend bundle at build time, so at first the
frontend image only worked against the one API address it was built with. The goal is *build
once, deploy the same image everywhere*. Since D3 the bundle calls the API at the path
`/api/v1` on its own host and the ingress routes `/api` to the backend, so one image serves
local, staging and production ([03-kubernetes.md](03-kubernetes.md)).
